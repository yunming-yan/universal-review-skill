# 实施前报告与修正方案

## 一份可审阅的决策依据

先给审查结论，再给推荐修正方案。可以在一个文件分节承载，保持版本、事实依据和实施状态清楚。报告和方案是实施输入，不是事后总结；已有报告无需为格式复制一套。

| 必须回答 | 具体内容 |
| --- | --- |
| 审什么、用于什么 | 对象与版本、用途/受众、有效要求、授权、实际覆盖及限制 |
| 哪里有问题、凭什么 | 稳定ID、准确位置、原始证据、事实/推断/缺口、影响和根因；错误与偏好分开 |
| 推荐怎么改 | 每项问题的最小修正、依据、拟改对象/字段/候选差异；有实际取舍才列备选及收益/代价/边界 |
| 改后是否自洽 | 数字定义与计算、状态/日期/术语、规则owner/适用制度、上下文及跨对象引用是否同版 |
| 还影响什么 | 上游来源、调用方、表格/公式/图表、脚本/模板、输出、索引及使用者；无需改的理由 |
| 怎么做、怎么证明 | 精确写集、依赖顺序、责任身份、已有授权、原件保存/恢复、逐项验证与非作者复核 |
| 还不能确定什么 | 缺失材料、工具/法源/签署能力、残余不确定性及真实业务待决；不补造数值/日期/批准人 |

对每个修正建立链：问题ID → 方案版本 → 候选/目标 → 实际操作 → 真实验证 → 异人终版结论。没有缺陷时写无修改及依据，不制造修正。

## 方案自身的逻辑闭环

- 最终结论是否能从已核事实和计算推出？缺口是被解决、明确限制，还是被文字掩盖？
- 同一指标的主体、期间、币种、税口径、分母、精度和状态是否唯一明确？不同口径有无分别标注？
- 每个动作的前提、资源、责任、时限或触发条件是否可实现？未确认的人员、预算与期限标拟议/待确认。
- 方案与附件/行动表/程序是否表达同一目标状态？建议、已批准、已执行不能混写。
- 一处修改是否让别处承诺、法律条件、公式、模板或使用入口失效？正式现行规则不能有两套互相冲突的权威。
- 是否仅修有据问题、保护既有合法内容和同期变更？成熟文本的合理风格和定性意见不因审者偏好重写。

重大或多对象方案先由不同作者的审查者看原源、候选、数字和依赖，不只读摘要；冲突未解就不实施相应动作。

## 呈现、执行与用户反馈

计划就绪时主动提供可访问报告/方案入口，概述关键修正与待决点。已有修改授权时，呈现后自动接续；不能把通知转成例行审批。没有修正授权时完成报告和获准的候选交付；用户明确“先给方案，等我决定”时等待其真实决定。

用户反馈改变需求时，核其与当前证据/授权的关系，说明不可由证据支持的部分并给可行替代。保留旧方案，另存修订版；已实施部分据实记录，待实施部分按新版本执行。新发现、失败和同期变化使用同样回路，不在旧已审方案外悄悄增加写入。

## 结案报告

最终报告将“建议修正”与“实际已修正/已验证”逐项对账；给最终成品版本、全部修改并集与影响、非作者复审证据、计算/法源/真实测试及未核项。文字整洁不等于事实就绪；内容审定不等于业务批准或实际发布。
