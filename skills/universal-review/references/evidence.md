# 证据、状态与交付

## 任务工作区

遵循任务指定的工作区；有既有检查点就接续，不能为了干净重建原基线。复杂、多阶段或会修改对象的审查保存可持续接力的证据包。小范围纯文本审阅可直接给可核定位和结论，不为了形式制造软件框架。

内容形式可沿用项目现有文件；以下信息槽必须真实覆盖，不能用空文件凑数。

| 信息槽 | 必须能回答 |
| --- | --- |
| 任务与授权 | 审什么、做到什么、能改什么、明确不包含什么、哪条要求有效 |
| 输入与版本 | 实际对象/路径或远端ID、内容版本/hash/时间、来源、历史副本与当前实物如何对应 |
| 覆盖 | 每个适用要求/目标由谁直接审、谁交叉、何种证据；排除和N/A的依据；未核项在哪里 |
| 审查身份 | 实际子代理/会话ID、任务、输入版本、运行与完成记录；作者和审查者关系 |
| 问题 | 稳定ID、位置、证据、影响、范围归类、严重度、处理与独立复核；旧发现/误报为何关闭 |
| 修正 | 修改前原件、必要性、精确候选/范围、授权、实际操作、diff、恢复和受影响检查 |
| 验证 | 实际命令/工具/输入版本、原stdout/stderr及立即返回码、完整结果/失败/skip；人工判断的原材料与理由 |
| 最终与接力 | 全修正集合、统一最终版本、实际交付/发布/必要重读、未闭环项、下一步和真实限制 |

## 原始证据的规则

保留真正的工具请求/响应、原文件、原运行、准确定位及版本关系。摘要必须指向原件；单写“已读/已派出/全部通过”不能证明动作发生。

只能获取部分平台记录时如实说明来源和缺口。本地保存的工具返回不冒充厂商签名；hash只能证明字节对应，不能证明模型理解、身份真实、用户意图或业务正确。没有原始记录不补造。

文件当前相等只能证明核对时的字节，不证明期间没有过短暂变化。未知写入状态保留并调查。历史输入用封存字节核，当前版本用当前实物核；不可把不同版本拼成一次通过。

保留原FAIL、异常、旧严重度、无效尝试和旧结论适用版本。修复不改写历史。敏感环境变量、凭据和私有材料只留在获授权的本地边界，公开报告使用必要字段与脱敏证据，不上传整份环境。

结构、业务与权限是三种结论：JSON齐全不等于业务PASS；测试exit0不等于验收满足；提示词写“只读”不等于OS已经限制写入。

## 状态与放行

| 状态 | 含义 |
| --- | --- |
| PASS | 明确范围内所有适用义务已核，问题闭环，最终版本一致 |
| LIMITED-SCOPE | 只完成被明确指定的局部范围；不是整体独审通过 |
| UNVERIFIED / PARTIAL | 有已核部分，但仍有来源、能力、覆盖或实际运行缺口 |
| BLOCKED | 某必要条件阻断相应动作；保留现场，继续无依赖工作 |
| NOT-APPLICABLE | 有可核理由证明该项不适用，不是没能力或没时间 |

发现已修正但尚未复核时，不称完成。未知不能通过改名、降严重度或过滤失败成为PASS。完整独审缺真实独立身份时，不能用角色数量、耗时、脚本总通过或自写多报告代签。

## 对用户的交付

先给实际结论及范围，然后给主要发现/修正、验证依据和仍需处理的限制。完整逐项证据留在可访问工作区，用户要求细节时提供。不要让一份冗长内部日志遮住真正结论。

报告与改稿区分：报告解释问题，改稿给目标读者直接使用。标明这次实际做过什么、未做什么；建议、计划、候选、已实施、已验证和已发布不得混写。

任何“全量”“独立”“通过”都必须有对应的实际范围和证据。严谨审查降低遗漏风险，不提供对任何模型、任何材料、任何任务的绝对正确保证。
